## What was in doubt

`design/ux/action-menu.md` commits to **three distinct attention states** — mouse-hover, board
cursor, and menu keyboard-focus — and said of the third:

> "it is the genuine Godot 4.6 dual-focus case — mouse focus and keyboard focus are separate
> subsystems and can both be live, so the focused row's indicator must be visually distinct from
> the hovered row's. ⚠ *Redot 26.2 fork parity on this behaviour is assumed, not verified.*"

Redot is a hard fork. Nothing had checked that the fork kept the behaviour the spec is built on.

## Result — 8 of 8 checks pass, deterministic across 3 consecutive runs

**State.** A focused row keeps `has_focus()` while a *different* row is hovered; that other row
reports `DRAW_HOVER`; hover never steals focus. The two subsystems are independent in this fork.

**Theme.** Rows resolve a `focus` StyleBoxFlat (border 2px, `(0.8, 0.8, 0.8)`, `draw_center =
false`) that is a different resource from `hover` (border 0, `draw_center = true`).

**Pixels.** Measured on a real framebuffer, each comparison being one row across two frames that
differ in exactly one thing:

| Cue | Ring delta | Pixels moved |
|---|---:|---:|
| **Focus** (same row, focused vs not) | **0.2428** | **17.9%** |
| **Hover** (same row, hovered vs not) | 0.0000 | 2.9% |

⇒ **Focus draws a box. Hover does not.** That is what makes them tellable apart, and it does not
depend on brightness — which matters, because `_make_row` deliberately sets `font_focus_color` and
`font_hover_color` to the *same* white, so brightness alone could never carry the distinction.

## ⚠ One finding the spec's owner should see — not a defect, a design call

**Hover renders, but only just.** It moves **2.9%** of a row's pixels — the glyphs, and only the
glyphs — lifting them from `LABEL_ENABLED` `(0.90, 0.94, 1.00)` to white. That is a ~3% brightness
change on text that is already near-white.

The cause is structural, not an oversight: rows are `flat = true`, which **suppresses the theme's
hover StyleBox entirely**, so hover has nothing but the font colour to work with. The focus box is
unaffected because Godot/Redot draw the focus StyleBox outside the flat check.

The spec's binding claim — *focus is distinguishable from hover* — **passes**. Whether hover should
itself be a legible attention state, when the spec promises three, is a design question this
harness has no standing to decide. **Recorded, not fixed.**

## ★ Two measurement bugs this found in itself, both worth remembering

Both are the Sprint 7 retro's rule 1 (*distrust clean results*) landing again, and both produced a
**confident, wrong, and plausible** answer before being caught.

1. **The focus outline is drawn entirely OUTSIDE the button's own rect.** Measured: a row at
   x 700..885, y 521..548 draws its border at x 699 / x 886 and y 519-520 / y 549-550 — the theme's
   focus StyleBox carries expand margins. The first pass sampled a 3px ring *inside* the rect,
   never touched a lit pixel, and reported **"the keyboard cue does not render"** about an outline
   plainly visible in the screenshot it had just saved. The tell was a delta of `0.0019` against an
   outline that should have moved the band by ~0.5.
2. **An average over a row hides a small mark.** Hover moves 3% of a row's pixels, which shifts the
   row's *mean* colour by 0.0013 — indistinguishable from noise. The harness reported "hover renders
   nothing" about a change that is really there. The tell was a delta of **exactly `0.0000`**.
   Fixed by counting pixels that moved rather than averaging the ones that didn't.

A third, different in kind: **the hover row's grown sampling band overlaps its neighbour's focus
outline**, so measuring hover as (both-live − neither) reported `0.107` of the *focused* row's cue
as this row's hover cue. Every comparison in the final harness is one row across two frames that
differ in one thing, for exactly this reason.

## ★ And one the project's own gate found

`export_safety_test.gd` failed the first working version: the harness reached for
`GameStateFactory`, which is declared under `tests/` — a directory the export preset strips. That
reference resolves in every build a developer runs and crashes in the shipped one. Inlined the
three lines it needed rather than adding the symbol to the allowlist, which is the fix the guard
itself asks for. **The guard did its job on a file written the same day.**

## Reproducing

```
DISPLAY=:0 ./redot tools/CaptureDualFocus.tscn      # exits 0 on PASS, 1 on FAIL
```
⚠ Needs a display. The engine-state half would pass headless; the "are they visually distinct" half
is a question about drawn pixels and the dummy rasteriser produces none — the same false positive
that hid the Story 007 glow bug behind a green suite.

⚠ **Not established by this run:** nothing was tested on a Steam Deck, and this is a desktop
1600×900 window, not the 1280×800 floor. The focus box is a 2px outline at any resolution, so it
does not thin out — but its *comfort* at 7 inches is untested, like every other legibility figure
in `technical-preferences.md`.
